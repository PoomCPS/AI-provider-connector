Foundation

Why Did We Build This in Rust? (The Core Mindset)

Imagine you are building a unified bridge connecting OpenAI, Anthropic Claude, and Google Gemini. Thousands of users are sending prompts, tools are executing, and token streams (SSE) are streaming simultaneously. Why not just write this in Python or TypeScript / Node.js?

❌ Python / Node.js Hazards
  • Primitive Obsession: An API key is just a string. Someone can log it, print it, or pass an empty string without warning.
  • Null Pointer & Runtime Crashes: TypeError: Cannot read properties of undefined strikes in production at 3 AM.
  • Memory & SSE Pressure: Keeping 5,000 open Server-Sent Events (SSE) connections in Node or Python consumes gigabytes of RAM.
  • Data Races: Mutating shared caches across threads without locks leads to corrupted state.
✅ The Rust Superpowers Used Here
  • Newtype Pattern: ApiKey is an opaque struct. It is impossible to log the plain secret by mistake.
  • No Null: Option<T> and Result<T, E> force you to handle missing values and errors at compile time.
  • Zero-Cost Streams: BoxStream streams tokens with minimal memory overhead, zero garbage collection pauses.
  • Fearless Concurrency: Arc<RwLock<...>> guarantees at compile-time that multiple threads cannot cause data races.
💡 The Rust Golden Rule
"Make illegal states unrepresentable." If a state should never happen at runtime (e.g., an empty API key, an unhandled HTTP 429 status, or a forgotten provider branch), write your Rust types so that the compiler refuses to compile the code if that state is possible.

🤔 WHY use a Cargo Workspace? (Beginner Question)
In Node.js, people often put everything in one big folder. But in Rust, compiling a web framework (like Axum) takes time. By separating crates/core from crates/server:
1. Another developer can import ai-provider-connector-core as a pure Rust library without pulling in Axum, HTML dashboards, or HTTP networking!
2. Build caching is faster: changes to the server dashboard do not force recompilation of the core AI adapter logic.

Module 2

The "Newtype" Pattern & Secret Leak Prevention

crates/core/src/types/api_key.rs

In Python, an API key is just api_key: str. But what if someone passes an empty string? Or what if an attacker injects newline characters \r\n to perform HTTP header injection? Or worse: what if your logging library accidentally dumps the plaintext API key into CloudWatch/Datadog?

Rust solves this with a world-famous idiom called the Newtype Pattern. Look at crates/core/src/types/api_key.rs:

crates/core/src/types/api_key.rs 
/// A tuple struct with a private field (String).
/// The caller CANNOT write `ApiKey("my-secret".into())` directly!
#[derive(Clone, PartialEq, Eq)]
pub struct ApiKey(pub(crate) String);

impl ApiKey {
    /// The ONLY way to create an ApiKey is through this constructor.
    pub fn new(raw: &str) -> Result<Self, ApiKeyError> {
        if raw.is_empty() {
            return Err(ApiKeyError::Empty);
        }
        if raw.len() > 4096 {
            return Err(ApiKeyError::TooLong(raw.len()));
        }
        // Validate bytes: strictly printable ASCII, NO control chars!
        for (i, b) in raw.bytes().enumerate() {
            if !(0x20..=0x7E).contains(&b) {
                return Err(ApiKeyError::InvalidHeaderCharacter(i));
            }
        }
        Ok(Self(raw.to_string()))
    }

    /// Explicit getter: you must intentionally call expose_secret()
    pub fn expose_secret(&self) -> &str {
        &self.0
    }
}
🔒 The Secret Weapon: Custom Debug Trait
Notice lines 65-69 in api_key.rs: 
impl std::fmt::Debug for ApiKey {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "ApiKey(\"***\")")  // NEVER prints the real key!
    }
}
In Rust, when you use tracing::info!("{:?}", connector_config), Rust calls this fmt method. Because we manually implemented Debug instead of using #[derive(Debug)], the API key is physically impossible to leak in debug logs!
Module 3

Enums in Rust Are Algebraic Data Types (Not C Enums)

crates/core/src/adapter.rs

If you come from TypeScript, Java, or C++, an enum is usually just a list of numbers: 0, 1, 2. In Rust, an enum is an Algebraic Data Type (Tagged Union). Each variant can carry completely different data!

Look at crates/core/src/adapter.rs:

crates/core/src/adapter.rs 
#[derive(Debug, thiserror::Error, Clone, PartialEq, Eq)]
pub enum AdapterError {
    // Variant 1: Carries an optional Duration (e.g. from Retry-After header)
    #[error("rate limit exceeded")]
    RateLimit { retry_after: Option<Duration> },

    // Variant 2: Unit variant (no data attached)
    #[error("service unavailable")]
    ServiceUnavailable,

    // Variant 3: Tuple variant holding an error message string
    #[error("authentication failed: {0}")]
    AuthenticationFailed(String),

    // Variant 4: Struct-like variant with multiple named fields!
    #[error("provider HTTP {status}: {message}")]
    Http {
        status: u16,
        message: String,
        retry_after: Option<Duration>,
    },
}
🎯 Exhaustive Pattern Matching: The Compiler Won't Let You Forget
When checking if an error is retryable in is_retryable(&self): 
match self {
    Self::RateLimit { .. } => true,
    Self::ServiceUnavailable => true,
    Self::Http { status, .. } => *status == 429 || *status == 503,
    Self::Network(_) => true,
    Self::AuthenticationFailed(_) | Self::InvalidRequest(_) => false,
    _ => false,
}
If you add a new error variant tomorrow, Rust will check your match statements at compile-time. You can never have an unhandled case slip into production!
Module 4

Zero Nulls, Zero Exceptions: Result<T, E> & the ? Operator

crates/core/src/connector.rs

Tony Hoare (inventor of the null pointer) called it his "billion-dollar mistake". Rust does not have null, and it does not use try / catch for normal error handling. Instead, every function that can fail returns Result<T, E>:

Option<T> (Value might be missing)

Used for optional things (e.g. retry_after: Option<Duration>)

enum Option<T> {
    Some(T),
    None,
}
Result<T, E> (Operation might fail)

Used for fallible operations (e.g. HTTP call, validation)

enum Result<T, E> {
    Ok(T),
    Err(E),
}
❓ The Magical Question Mark Operator (?)
How do we avoid writing 100 nested if let Ok(...) blocks? Look at line 40 in connector.rs: 
let client = config
    .tls
    .build_client()
    .map_err(|e| AdapterError::Other(e.to_string()))?;  // <-- Notice the '?'
What does ? do?
1. If build_client() returns Ok(client), it unwraps the inner value and puts it in client.
2. If it returns Err(e), the function immediately returns Err(e) to the caller!
It's like an automatic, type-safe return-early guard, completely eliminating pyramid-of-doom callbacks!
Module 5

Polymorphic Adapters: Traits vs Dynamic Dispatch (dyn Trait)

crates/core/src/adapter.rs & connector.rs

Our connector supports OpenAI, Anthropic, and Gemini. Each provider has completely different JSON schemas and REST endpoints. How do we unify them behind a single interface without repeating code?

We define a Trait (Rust's equivalent to an interface, but zero-cost by default):

crates/core/src/adapter.rs 
/// The single primary seam for all AI providers
#[async_trait]
pub trait ProviderAdapter: Send + Sync {
    /// Non-streaming completion
    async fn complete(&self, request: &CompletionRequest) 
        -> Result<CompletionResponse, AdapterError>;

    /// Real-time token streaming
    async fn stream(&self, request: &CompletionRequest) 
        -> Result<BoxStream<'static, Result<StreamChunk, AdapterError>>, AdapterError>;
}
🧠 Why Arc<dyn ProviderAdapter> instead of Generics? (Click to expand)
In Rust, you can do polymorphism in two ways:

1. Static Dispatch (Generics: struct Connector<A: ProviderAdapter> { adapter: A }): The compiler generates specialized assembly for each adapter at compile time (monomorphization). Extremely fast, but the type of Connector depends on the provider. You can't store OpenAI and Anthropic in the same array or web server state easily without complex type parameters.

2. Dynamic Dispatch (Trait Objects: Arc<dyn ProviderAdapter>): The dyn keyword tells Rust to use a vtable (virtual method table) pointer. This allows us to store any adapter inside the web server's AppState, swap adapters at runtime, or inject mock adapters in unit tests!
Module 6

Ownership, Borrowing, Arc & RwLock (Thread Safety)

crates/server/src/state.rs

This is the #1 hurdle for Rust beginners: The Borrow Checker. Rust enforces three iron rules at compile time:

1. Single Owner

Every piece of memory has exactly one owner variable. When that owner goes out of scope, the memory is instantly freed.

2. Shared References (&T)

You can have unlimited immutable borrows (readers). No one is allowed to modify the data while readers exist.

3. Mutable Reference (&mut T)

You can have at most ONE mutable borrow (writer). While writing, no readers or other writers are allowed. Zero data races!

Now look at crates/server/src/state.rs. In a multithreaded web server, dozens of HTTP requests hit our server simultaneously. How do we share state?

crates/server/src/state.rs 
#[derive(Clone)]
pub struct AppState {
    // Atomic Reference Counted trait object:
    pub secret_store: Arc<dyn SecretStore>,
    
    // Thread-safe Read/Write lock wrapping a HashMap:
    pub adapter_overrides: Arc<RwLock<HashMap<ProviderKind, Arc<dyn ProviderAdapter>>>>,
}
🔍 Anatomy of Arc<RwLock<T>>
What is Arc<T>?
Stands for Atomic Reference Counting. It lets multiple threads hold a pointer to the same heap data. When the last thread drops its Arc, the data is automatically deallocated.

What is RwLock<T>?
Stands for Reader-Writer Lock. Multiple HTTP requests can read .read() simultaneously at full speed. But when a test injects an override via .write(), it safely waits until all readers finish.
Result: 100% thread safety guaranteed by the compiler. No segfaults, no deadlocks!
Module 7

Async Rust & Real-Time Token Streaming (Tokio + BoxStream)

crates/core/src/connector.rs & retry.rs

Unlike Go (which uses green threads with goroutines) or JavaScript (which has a single event loop), Rust's async model is zero-overhead and pull-based. A Rust Future does nothing until it is actively polled by an executor (like Tokio)!

Look at how retries are handled in connector.rs:

crates/core/src/connector.rs 
pub async fn complete(&self, request: &CompletionRequest) 
    -> Result<CompletionResponse, ConnectorError> 
{
    let mut attempt = 0;
    loop {
        match self.adapter.complete(request).await {
            Ok(resp) => return Ok(resp),
            Err(err) => {
                attempt += 1;
                if !err.is_retryable() {
                    return Err(ConnectorError::Adapter(err));
                }
                if attempt >= self.config.retry_policy.max_attempts {
                    return Err(ConnectorError::RetriesExhausted {
                        attempts: attempt,
                        last_error: err,
                    });
                }
                // Non-blocking sleep: frees OS thread to process other requests!
                let delay = self.config.retry_policy.compute_delay(attempt - 1, err.retry_after());
                tokio::time::sleep(delay).await;
            }
        }
    }
}
⚡ Why tokio::time::sleep Instead of std::thread::sleep?
If you call std::thread::sleep(delay), you physically block an entire OS thread. If all 8 threads on your CPU are sleeping, your server can't handle a single incoming request!
When you call tokio::time::sleep(delay).await, Tokio simply pauses that individual task and immediately schedules other HTTP requests on that CPU core. Zero wasted resources!

Axum 0.8: Type-Safe HTTP Routing & Handlers

crates/server/src/routes/completions.rs

How does the server accept requests? In Express or Flask, request objects are dynamically typed dictionaries. In Axum (Rust's premier web framework built on Tokio and Tower), everything is statically typed using Extractors:

crates/server/src/routes/completions.rs 
pub async fn handle_completions(
    // 1. Extractor: Type-safe shared application state
    State(state): State<AppState>,
    // 2. Extractor: Deserializes JSON payload directly into typed struct
    Json(payload): Json<ServerCompletionRequest>,
) -> Result<Response, ServerError> {
    // If the JSON from the browser was invalid, Axum rejected it
    // BEFORE this function even began! Zero manual validation code needed!
    
    if payload.request.stream {
        // Returns Server-Sent Events (SSE) stream
        let stream = connector.stream(&payload.request).await?;
        Ok(Sse::new(stream_response).keep_alive(KeepAlive::default()).into_response())
    } else {
        // Returns standard JSON completion
        let resp = connector.complete(&payload.request).await?;
        Ok(Json(resp).into_response())
    }
}
🎨 IntoResponse: Clean Error Propagation
Notice the return type: Result<Response, ServerError>. Because ServerError implements Axum's IntoResponse trait, we can use the ? operator throughout our handler. If an error occurs, Axum automatically converts our ServerError into the proper HTTP status code (e.g. 403 Forbidden or 429 Rate Limited) and JSON error response!
